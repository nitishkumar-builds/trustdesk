# TrustDesk — standing brief

Read this file before every phase. `TRUSTDESK_CLAUDE_CODE_PROMPTS.md` holds the phase-by-phase build plan; `TRUSTDESK_PROBLEM_STATEMENT.md` is the source of truth for scope.

## Project summary

1. TrustDesk is an AI-first customer support operations platform built for the Airtribe capstone.
2. It ingests policy documents, triages tickets (category / priority / sentiment / escalation), and generates grounded draft replies with `KB-*` citations.
3. The AI only recommends tool actions; sensitive actions need explicit human approval and an idempotency key before execution.
4. Every AI run leaves an `AgentRun` trace, and an eval runner scores the 8 cases in `data/eval_cases.jsonl` (triage, citations, unsafe-action blocking, escalation).
5. Guardrails treat customer text and retrieved documents as untrusted, refuse secret/identity-bypass/injection requests, and quarantine `KB-ADVERSARIAL-001`.

## Read-only capstone pack

`data/`, `docs/`, `scripts/`, `TRUSTDESK_PROBLEM_STATEMENT.md` and `TRUSTDESK_CLAUDE_CODE_PROMPTS.md` are the provided pack. Never modify, move, or delete anything inside them. Project-authored docs go in `docs_project/` (Phase 10).

Repo root holds only: config files, `CLAUDE.md`, `README.md`, `docker-compose.yml`, `docs_project/`, `reports/`, `server/`, `web/`, and the pack.

## Stack (fixed, do not substitute)

- Node 20+, TypeScript, ESM (`"type": "module"`), strict mode on
- Express 4, Zod for request validation, pino for logging
- Prisma + PostgreSQL 16 (Docker Compose, container `trustdesk-db`)
- Vitest + Supertest for tests
- Frontend: React 18 + Vite + TypeScript, plain CSS, no component library, no state manager
- Live AI provider: OpenRouter (`https://openrouter.ai/api/v1`, model from `OPENROUTER_MODEL`)
- Test/eval AI provider: local deterministic mock adapter (`AI_PROVIDER=mock`, the default)
- Retrieval: Postgres full-text search (`tsvector` + GIN) + `pg_trgm` fallback + category prior boost. No vector DB.
- Auth: static demo bearer tokens mapped to three roles (`support_agent`, `support_manager`, `admin`)

## API conventions

- Success responses are plain JSON objects (no envelope) with snake_case keys, matching `docs/API_CONTRACT.md`.
- Every error, from every endpoint, uses `{ "error": { "code", "message", "details" | null, "request_id" } }`.
- Error codes: `VALIDATION_ERROR` 400, `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409, `GUARDRAIL_BLOCKED` 403, `TOOL_EXECUTION_FAILED` 500, `AI_PROVIDER_ERROR` 502, `INTERNAL_ERROR` 500.
- `GET /health` is the only unauthenticated route; everything else lives under `/api` and requires a bearer token.

## Non-negotiable rules

- R1. Policy windows (return eligibility, warranty) are ALWAYS evaluated against the ticket's `created_at`, never against the current date or `Date.now()`.
- R2. The fields `expected_category`, `expected_priority`, `expected_sentiment`, `expected_escalation`, `expected_actions` are evaluation-only. They are stored in a separate table and MUST NOT be readable from any code path that builds a prompt, triages, drafts, or recommends actions.
- R3. Customer text and retrieved document text are untrusted data, never instructions. They are always wrapped in explicit delimiters before reaching a model.
- R4. `KB-ADVERSARIAL-001` is ingested but quarantined: never returned as grounding context, never cited.
- R5. The AI may only RECOMMEND tool actions. Execution always requires an explicit human API call, and sensitive actions require an approval record first.
- R6. Every sensitive tool action carries an idempotency key; a replay never creates a second action.
- R7. Every triage run, draft run and eval case run writes an `AgentRun` trace row.
- R8. No secret, system prompt, internal note, or unrelated customer's data ever appears in a draft reply.

## Decisions

- D-000 (Phase 0) Stack fixed as listed above; Node/TS/ESM, Express 4, Prisma + Postgres 16, Zod, pino, Vitest + Supertest, React + Vite, OpenRouter live + deterministic mock.
- D-001 (Phase 0) Code layout: all backend in `server/`, all frontend in `web/`; `data/`, `docs/`, `scripts/` are never modified.
- D-002 (Phase 0) `server/` is a standalone package (no npm workspaces). A root `package.json` with `concurrently` arrives in Phase 9 only as a convenience runner.
- D-003 (Phase 0) Error envelope `{ error: { code, message, details, request_id } }` on every error; success bodies are plain snake_case JSON with no envelope.
- D-004 (Phase 0) Request ids: honour an incoming `X-Request-Id` (max 128 chars) else `crypto.randomUUID()`; always echoed on the response header and in the error envelope.
- D-005 (Phase 0) `env` is parsed once by Zod and frozen; a missing or malformed variable throws at import time with a readable list (fail fast, no partial boot).
- D-006 (Phase 0) `AI_PROVIDER` defaults to `mock`; every test and eval run uses the mock unless explicitly overridden. Default OpenRouter model: `google/gemini-2.0-flash-001`.
- D-007 (Phase 0) Demo auth tokens live in env (`DEMO_AGENT_TOKEN`, `DEMO_MANAGER_TOKEN`, `DEMO_ADMIN_TOKEN`) mapping to `support_agent` / `support_manager` / `admin`.
- D-008 (Phase 0) Version pins chosen because the prompt did not specify them: Prisma 6.x (schema-file datasource URL, stable migrate workflow), Vitest 3.x, TypeScript 5.9.x, ESLint 8.x (so `.eslintrc.json` is honoured), Zod 3.x. Lint is non-blocking.
- D-009 (Phase 0) `vitest.config.ts` sets `passWithNoTests: true` so `npm test` is green before the first suite lands in Phase 1.
- D-010 (Phase 0) `docker-compose.yml` adds a `pg_isready` healthcheck so `docker compose ps` reports `healthy`, satisfying the Phase 0 acceptance check.
- D-011 (Phase 0) Unknown routes return the standard envelope with `NOT_FOUND` (a catch-all is registered just before `errorHandler`).
- D-012 (Phase 1) Schema: pack natural string ids are primary keys; generated ids are `newId(kind)` in `server/src/db/ids.ts` = prefix (`draft_`, `run_`, `act_`, `appr_`, `eval_run_`, `fb_`) + cuid2. Models map to snake_case tables/columns via `@@map`/`@map`. Money is `Int` whole rupees; currency is a string.
- D-013 (Phase 1) Dates: date-only pack values are stored as `DateTime` at 00:00 UTC; ticket `created_at` is stored as the instant it denotes (`timestamptz`), so `+05:30` semantics survive. Every `DateTime` column is `@db.Timestamptz(3)`.
- D-014 (Phase 1) `knowledge_chunk.search_vector` is a Postgres `GENERATED ALWAYS ... STORED` tsvector created by migration `add_fts` (drop-then-add, because the init migration had already created a plain column). The Prisma schema mirrors it with `@default(dbgenerated(...))` plus the two GIN indexes (`type: Gin`, `ops: raw("gin_trgm_ops")`) so `prisma migrate dev` reports no drift. Prisma cannot write the column; Postgres computes it.
- D-015 (Phase 1) Seeder idempotency: every pack entity is `upsert`ed by natural id. Knowledge chunks have generated ids, so each document's chunk set is replaced (delete + createMany) inside one transaction; counts are identical on every run. `--reset` truncates all 15 tables with `CASCADE` first.
- D-016 (Phase 1) Knowledge chunking: split on `## ` headings; the preamble (H1 + `Doc ID`/`Audience`/`Version` lines) is not a chunk unless prose remains after removing those lines; a document with no H2 becomes one chunk. Result: 25 chunks across 8 documents.
- D-017 (Phase 1) Return window: `eligible_return_until` wins, else `delivered_at + 7 days`; the whole calendar day of the window end counts as inside. Check order: `final_sale` → `non_returnable_category` (category `software`) → `not_delivered` → date comparison. So ord_5004 (software AND final sale) reports `final_sale`.
- D-018 (Phase 1) Warranty: base 12 calendar months from `delivered_at` (UTC month arithmetic, end date inclusive). Gold adds 6 months only when EVERY item is extension-eligible (not software, not final sale, not an accessory under INR 3000). Item price = `unit_price` if the item carries one, else `order.total / total quantity` (the pack has single-item orders and no per-item price). `monthsSinceDelivery` = days / 30.4375 rounded to 2 dp; `null` when undelivered.
- D-019 (Phase 1) `prisma migrate dev` is interactive on drift and will hang or prompt to reset under a non-TTY; always run it with stdin closed (`< /dev/null`) in scripts, and never accept a reset against a seeded DB without re-seeding. If an advisory-lock timeout appears, an orphaned `schema-engine` process is holding it — kill it and terminate its Postgres backend.
- D-020 (Phase 2) Auth: `requireAuth` is applied once on the `/api` router in `app.ts`, so every feature router is authenticated by construction; `requireRole(...roles)` is added per route where a phase demands it. `req.principal` is `{ userId, role }`; `getPrincipal(req)` throws instead of returning undefined.
- D-021 (Phase 2) `GET /api/tickets?category=` filters on the LATEST triage result. Prisma cannot express "latest child matches", so with a category filter the service loads the (status-filtered) tickets, filters in memory, and paginates the result. Without it, pagination is done in SQL. Default sort is `created_at asc`.
- D-022 (Phase 2) `policy_context` on ticket detail: `as_of` = ticket `created_at`; `return_window` and `warranty` are both `null` when the ticket has no order (the prompt only specified `warranty | null`).
- D-023 (Phase 2) `POST /api/tickets` also rejects (400 `VALIDATION_ERROR`) an `order_id` that exists but belongs to a different customer; ids are `tkt_` + 8 alphanumerics from `crypto.randomBytes`; status starts as `open`; 201 on create.
- D-024 (Phase 2) Tests: `tests/setup.ts` forces `NODE_ENV=test`, `LOG_LEVEL=silent` (override with `TEST_LOG_LEVEL`), probes `DATABASE_URL` once with a 5 s timeout, and DB-backed suites wrap themselves in `describeWithDb()` (`tests/helpers/db.ts`) so they show as skipped with the reason instead of failing. API tests delete the tickets they create in `afterAll`, so `total === 8` holds on every run.
- D-025 (Phase 3) Retrieval is chunk-level: `searchKnowledge` returns `{ doc_id, title, chunk_id, heading, snippet, score, source, trust_level }` rows (a superset of `docs/API_CONTRACT.md` section 2). `trust_level` rides along so `buildGroundingContext` can label each fence without a second query.
- D-026 (Phase 3) Stage A runs `websearch_to_tsquery` twice when needed: the strict all-terms form first (its rows get a +0.25 full-match bonus, because `ts_rank_cd` flattens OR-query scores), then, if fewer than 2 rows, the same terms OR-joined so a query containing a word absent from the KB ("earbuds") still ranks partial matches. Stage B (`similarity(content, q) > 0.15`) is kept as specified but almost never fires on chunk-sized text (observed maximum ≈ 0.05); it is a safety net, not the workhorse.
- D-027 (Phase 3) Category prior (`categoryPriors.ts`): with a `categoryHint`, the mapped document's best-matching chunk is guaranteed a result slot (inserted if absent, first chunk as a last resort) and its score is boosted by +0.5, source `category_prior`. This is a deliberate reliability measure for graded citation coverage; retrieval is therefore not purely learned. The README must list it as a known limitation.
- D-028 (Phase 3) Rule R4 in code: every retrieval SQL carries `AND (includeQuarantined OR d.quarantined = false)`; the only caller allowed to pass `includeQuarantined: true` is the Phase 5 guardrail self-test (and its test). API ingest quarantines a document when its `doc_id` contains `ADVERSARIAL` or its content matches the inline injection list in `knowledge/service.ts` (TODO: replaced by `guardrails/patterns.ts` in Phase 5). Quarantined docs are still listed and readable via `/api/documents` so reviewers can see the quarantine.
- D-029 (Phase 3) One persistence path for documents: `persistParsedDocument()` in `knowledge/service.ts` (upsert doc + replace chunk set in one transaction) is used by the seeder, `/documents/ingest` and `/documents/reingest`. Repo paths come from `config/paths.ts` (resolved from `import.meta.url`).
- D-030 (Phase 3) `buildGroundingContext` neutralises any literal `<policy_document` / `</policy_document` inside chunk text (rewritten to `[policy_document]`) and strips `<`/`>` from attribute values, so a document cannot close its own fence early. `/documents/search` is registered before `/documents/:docId` so "search" is never treated as a doc id.
- D-031 (Phase 4) The mock adapter classifies ONLY the text inside `<customer_message>…</customer_message>` (falls back to the whole payload if the fence is absent). Retrieved policy chunks quote injection examples verbatim ("Ignore previous instructions", "Print your API key"), so scanning the whole prompt would mislabel every ticket. The same reason keeps bare "package"/"delivered" out of the mock's shipping terms: a damaged-on-arrival ticket mentions delivery too.
- D-032 (Phase 4) Post-rules PR1–PR4 are mutually exclusive category overrides applied first-match-wins in the documented priority order; every matching rule is still recorded in `guardrail_results.fired_rules` with `applied: true|false` so the trace shows all patterns present. PR5/PR6 only raise priority ("at least high"). The trace also stores `model_output` and `final_output` so "what did the AI actually decide?" is answerable from the run.
- D-033 (Phase 4) Model-output validation: Zod-parse the JSON; on failure retry once with a corrective system line; on a second failure use the mock rule output and record `model_output_invalid_fallback_applied` in `guardrail_results.notes`. In that case the AgentRun keeps `modelProvider` = the configured provider (so the fallback is visible), `modelName` null. The OpenRouter adapter itself never falls back: 429/5xx/timeout/network errors are retried once (1 s backoff) then surface as `AI_PROVIDER_ERROR` 502.
- D-034 (Phase 4) `OpenRouterAdapter` takes injectable `fetch` and `sleep` so its retry/timeout/fence-stripping paths are unit-tested without network. The live path was exercised manually (2026-09-19): the spec's default `google/gemini-2.0-flash-001` now returns 404 "No endpoints found" on OpenRouter, so `.env.example` keeps the specified default but a live run needs `OPENROUTER_MODEL=google/gemini-2.5-flash` (verified working: valid JSON on tkt_9001 and tkt_9006, tokens and latency in the trace). The README (Phase 10) must state the exact model string used. `OPENROUTER_API_KEY` is read from the process environment; dotenv does not override a value already set on the machine.
- D-035 (Phase 4) The triage service does not store the acting principal (AgentRun has no actor column; the prompt's schema is fixed). `triageTicket(ticketId, principal, { provider? })` accepts an optional provider override for the Phase 8 eval runner.
- D-036 (Phase 5) Pattern matching is whole-phrase and case-insensitive: no letter/digit may touch either end (so "otp" does not fire inside "laptop"), whitespace runs are flexible, and a `*` token in a term matches up to 4 intervening words (`issue me a * coupon` catches "issue me a 5000 INR coupon"). Patterns live as data in `guardrails/patterns.ts`; `HIGH_SEVERITY_GROUPS` and `DOCUMENT_REJECT_GROUPS` are the two derived sets.
- D-037 (Phase 5) For retrieved DOCUMENTS only, text inside quotation marks is blanked before scanning: KB-SECURITY-001 legitimately quotes injection examples ("Ignore previous instructions."), and scanning them would reject the security playbook and quarantine it on API re-ingest. The adversarial note's instruction is unquoted and is still rejected. Customer messages never get this exemption.
- D-038 (Phase 5) `SearchResult` now carries the full chunk `content` and the doc's `quarantined` flag. `assessDocuments` scans content (a 40-word snippet could hide an instruction) and `buildGroundingContext` grounds on content rather than the snippet. The Phase 3 inline injection list in `knowledge/service.ts` is gone; ingest quarantine now uses the same INSTRUCTION_OVERRIDE / CONCEALMENT groups as document trust.
- D-039 (Phase 5) Output-scanner severities: LEAKED_SECRET, LEAKED_INTERNAL_NOTE, UNGROUNDED_CITATION, CROSS_CUSTOMER_DATA and UNSAFE_PROMISE are high (safe=false → Phase 6 swaps in the `unsupported_policy_request` refusal); MISSING_CITATION is low because the draft pipeline appends the guardrail's required citations after the scan, so it is recorded, not blocking. "Quotes without paraphrase" = a run of 8+ consecutive words shared with a document whose audience is not "Customer support agents". `scanDraftOutput` takes injectable loaders (customers, internal docs) so it is unit-tested without a DB.
- D-040 (Phase 5) Decision-table nuance: PRIVILEGE_ESCALATION on its own is low severity, so a polite "could you give me a coupon" is not refused; it refuses only alongside a high group (tkt_9006 has INSTRUCTION_OVERRIDE + CONCEALMENT). The decision also returns `refusalTemplate` so Phase 6 does not re-derive which template to use. `guardrails/selfTest.ts` is the single sanctioned `includeQuarantined: true` caller (D-028) and proves retrievable-when-asked + rejected-by-document-trust against the live index.
- D-041 (Phase 6) "PR1 fired in triage" is recomputed from the customer text with `applyPostRules` (a pure function) instead of being read back from the triage trace, so the safety gate cannot drift from what triage decided and Phase 7 can evaluate it without a stored trace. `caseRuleContextForTicket()` in `drafts/service.ts` rebuilds the full case context (category, guardrail outcome, safety, return window, shipping facts) for Phase 7's execution gate; `blockedToolsForCase()` lists every tool the case forbids.
- D-042 (Phase 6) Citations: the output scan's `allowedDocIds` = safe retrieved doc ids ∪ the guardrail's required citations (KB-SECURITY-001 / KB-ACCOUNT-001 are grounded by policy even when retrieval did not surface them). On the refuse path citations = required ∪ safe retrieved (per prompt, so extra retrieved docs such as KB-COUPON-001 appear; evals check subset). When the output scan fails, any citation outside `allowedDocIds` is dropped before the draft is stored, so a fabricated doc id never persists. Required citations are appended last, de-duplicated, order preserved.
- D-043 (Phase 6) When the guardrail outcome is not `allow` and the surviving recommendations do not include `escalate_to_human`, it is added deterministically (reason names the outcome). This is still only a recommendation (rule R5) and keeps allowed_action_recall from depending on whether a live model remembered to propose escalation.
- D-044 (Phase 6) Recommendation rules (`drafts/recommendationRules.ts`), first strip wins: unknown tool → category not allowed → guardrail refusal (only escalation) → safety case (only escalation; replacement and coupon explicitly stripped) → return window not eligible (refund category only; a billing duplicate-charge refund review must not depend on the return window) → stale tracking (shipping, order not delivered, business days since placed_at + 1 business day dispatch lead < 10, and no executed `open_carrier_investigation` whose result has `carrier_confirmed_lost: true`) → `issue_coupon` always stripped. issue_coupon is NEVER auto-recommended by this system: a human may request it in Phase 7, but the AI never suggests goodwill credit. Business days are Mon–Fri UTC with no holiday table (`domain/businessDays.ts`, rule R1 asOf).
- D-045 (Phase 6) Draft lifecycle (`PATCH /api/drafts/:id`): edited ← generated|edited|approved (body required); approved ← generated|edited; rejected ← generated|edited|approved (reason required); sent ← approved only; sent and rejected are terminal. Anything else is 409 CONFLICT naming the current status. approved/rejected write an Approval row (reviewer = principal). An edited body is re-scanned with the output scanner (rule R8 covers human edits) and rejected with 403 GUARDRAIL_BLOCKED when unsafe. Any role may approve a draft (the prompt scopes manager-only approval to tool actions in Phase 7).
- D-046 (Phase 6) Traces: `guardrail_outcome` and `confidence` are not columns on DraftReply (schema is fixed), so they live in the draft's AgentRun `guardrail_results` (`decision.outcome`, `confidence`) and the mappers join the run. A provider failure still writes an AgentRun with status `failed` and the error in `notes` (rule R7) before the 502 surfaces. On the refuse path `model_provider` is recorded as `none` (the model was never called).
- D-047 (Phase 6) Mock draft rules read only the labelled lines `buildUser` writes (`triage_category:`, `return_window: eligible=…`, `<policy_document id="…">`) and cite only ids that were actually retrieved; bodies are worded to avoid every phrase the output scanner and the eval answer requirements forbid (no "has been refunded", no troubleshooting verbs in the safety reply, no coupon offers). `vitest.config.ts` sets `fileParallelism: false` because DB-backed suites share one seeded database; the drafts suite runs a fresh mock triage before each draft so it never depends on leftover triage rows (a live-model triage left in the dev DB once flipped tkt_9001 to warranty).
- D-048 (Phase 6, post-review) Four defects found by the adversarial review were fixed with regression tests: (1) a chunk HEADING is now neutralised and bracket-stripped in `buildGroundingContext` and scanned together with the body in `assessDocuments` (a crafted H2 could previously close the `</policy_document>` fence — amends D-030); (2) `extractDraftFacts` strips the `<customer_message>` block before parsing the labelled fact lines and `<policy_document id>` tags, so a customer cannot forge `return_window:`/`triage_category:` lines for the mock or the live-model fallback; (3) `PATCH /api/drafts/:id` accepts a `body` only with `status: "edited"` (400 otherwise), so the text sent is always the text that was approved — amends D-045; (4) the transition is a conditional `updateMany(... status in allowedFrom)` inside the transaction, so concurrent approvals yield exactly one 200 / one 409 / one Approval row. Also: when a refund case is not eligible and the model body lacks a "not eligible"/"final sale" statement, a grounded sentence is appended (KB-REFUND-001 added to citations if retrieved) and `not_eligible_statement_appended` is noted, instead of only logging a note.
- D-049 (Phase 7) The execution gate reuses the Phase 6 case rules with scope `'execution'`: category, safety-first, return-window-not-eligible and stale-tracking block a human request exactly as they block a recommendation, but the two AI-conservatism rules (`guardrail_refusal → only escalation`, `issue_coupon never auto-recommended`) do not apply to a human who explicitly requests an approval-gated action. Without this split the prompt's own test (issue_coupon 500 on tkt_9006 → approval_required) is impossible, since tkt_9006 is a refuse_and_escalate case. The AI still never recommends coupons; a manager can still decline them.
- D-050 (Phase 7) `requestAction` also validates payload references at request time so an approved action cannot fail on a bad id later: `order_id` must be the ticket's linked order, `customer_id` the ticket's customer, `payload.ticket_id` the request ticket, and `start_refund_review.amount` ≤ the order total (400 VALIDATION_ERROR). `amount` must be a positive number; every other required field is a non-empty string. 201 on creation, 200 on an idempotent replay (`idempotent_replay: true`), the replayed payload is ignored.
- D-051 (Phase 7) State machine and concurrency: `approval_required → approved|rejected` (manager/admin, conditional update so a second concurrent approval gets 409), `approved → executing → executed|failed`, `requested → executing → executed|failed` (low-risk tools, inside the request that created them). `executing` is a transient claim taken with a conditional `updateMany`, so two concurrent executes run the executor once; a loser that arrives after completion gets the stored result with `idempotent_replay: true`, one that arrives mid-flight gets 409. `rejected`, `failed` and `executed` never execute again; `cancelled` is reserved. The registry (`toolActions/registry.ts`) loads ToolDefinition rows once (warmed in `index.ts`), fails loudly if a row has no executor, and exposes mutable `{ definition, executor }` entries so tests can spy on an executor. Every request (created or replayed) writes a `tool_recommendation` AgentRun whose `tool_calls[0].action_id` references the action; `model_provider` is `none`.
